## L1 设置页分组导航暴露为 `Toggle`，语义应为"选项卡"

**现象**：设置页三个分组（下载 / 网络 / 界面）在 UI Automation 树里是 `Button` + `Toggle=True`，屏幕阅读器念成"可切换按钮"，而不是"选项卡 1/3"。`Toggle` 也不传达"三选一互斥"。

**这是修复，不是退步**：改前用 `selectable_label`，**完全点不动**（无 `Invoke`、无 `SelectionItem`、无 `Toggle`，辅助技术与 UIA 脚本都无法驱动）。M3 的 R3 前置体检因它报过假红，修好后 PASS。

**能用性已证**：`Toggle` 可驱动、切换真的换组（下载组 8 个单选、网络组 0 个复选、界面组 12 个复选）、当前组有 `selected` 高亮。

**为什么不现在修**：要精确语义得让 egui 暴露 list/tab 角色，可能要把分组容器换成别的控件树；而当前形态是**真缺陷的修复**，先保"能点"。语义属打磨。

**该修的条件**：有屏幕阅读器用户反馈，或做无障碍专项。修时判据要一起改——`Toggle` 也可作为可接受形态之一，别把"非 TabItem 即失败"写成门禁。

## L3 管理员上下文 `--quit` 未实测

**现象**：控制管道名已按**当前用户 SID** 隔离（`\\.\pipe\ariahost-ctl-<SID>`，见 `docs/dev/release.md` §12），DACL 仍 allow `BA`（本机管理员）；但**没有实测过**管理员身份下 `--quit` 能否连上并停下管理员启动的面板。

**别把它当成 SID 问题**：UAC 提权**同一账户**不改变用户 SID（变的只是完整性级别与管理员组的启用状态），所以提权后的 `--quit` 算出的管道名与面板一致——安装器覆盖升级路径的真机实测就是 `quit: accepted`（面板随即退出）。只有**换账户提权**（over-the-shoulder，界面里输入另一个管理员的凭据）才换 SID，那时回 `no-instance`（exit 0），安装器靠 tasklist 复查发现进程仍在 → Abort 并提示（交互见 `docs/dev/release.md` §12）。

**为什么没测**：本机会话审批被禁、取不到提权令牌（UAC 必须人来点）。**不是设计问题，是取证边界。**

**已覆盖的风险**：非管理员路径已实测通过（`accepted` exit 0、面板 1–7s 内退出、无残留——硬上限是安装器 20s 预算）。"不同用户互不误杀"不再靠 DACL 兜底，而是**名字隔离 + 不回退旧名**：真机实验里先建一个旧固定名 `\\.\pipe\ariahost-ctl` 的假服务端，再跑 `--quit`，结果 `no-instance`（exit 0）且假服务端**收到 0 字节**（task-56 验收 3）。

**该修的条件**：有管理员用户报 `--quit` 失败，或做安全审计。手工验收项见 `.scratch/m3/manual-acceptance.md`。

## L4 egui 的 accesskit 只消费 `Click`：`SetValue` / `Toggle` / `SelectionItem` 显式驱动无效

**现象**（源码级已定位，`egui 0.37`）：

| 控件 | UIA 暴露 | 实际效果 |
|---|---|---|
| `Button`（含分组导航） | `Invoke` / `Toggle` | **可驱动** |
| `TextEdit` | `ValuePattern.SetValue` | **不生效**：provider 回声新值，但 app 状态未变（铁证：`保存` 一直 `disabled`——`is_dirty()` 若为真必变亮） |
| `RadioButton` | `SelectionItem.Select` | 空转（egui 不消费该动作） |
| `CheckBox` | `TogglePattern.Toggle` | 空转 |

根因：`egui-0.37.0/src/context.rs:1769` 只处理 `input.has_accesskit_action_request(id, Action::Click)`；`response.rs:1001/1004` 只注册 `Focus` 与 `Click`。`rich_text_editor/builder.rs:1128` 虽然 `add_action(Action::SetValue)`，但返回值没有被应用到文本状态。

**影响**：屏幕阅读器 / 语音输入 / 自动化脚本只能"发现并点击"，**不能"程序化设置值"**。对只用键盘的用户不构成阻断（Tab + 打字可用），但比鼠标用户多一道门槛。

**这直接影响我们的取证方式**：UIA 驱动不了改值类验收条目。已定的做法是在面板里加**隐藏自检驱动**（`--panel-selftest --drive …`：把合成事件灌进 `egui::RawInput` 跑真正的 `ui()`），**不碰 Win32 输入、不需要解锁、可在 CI 跑**。

**为什么不现在修**：这是 egui 上游行为，改它要 fork/补丁整条输入链路；且修好也没有用户可见收益（键盘用户不受阻）。

**该修的条件**：egui 上游支持；或有屏幕阅读器用户明确要求"用语音设置数值"。届时判据要一起改，别把"必须支持 `SetValue`"写成门禁。

## L5 上游 aria2 关闭本身需 ~4.1 秒（非本产品可控）

**现象**：发 `aria2.shutdown` 或 `forceShutdown` 之后，`aria2c.exe` 进程**自身**要 **4.1 秒**才退出（空载、无任务也一样）。

**影响**：面板"退出时停 aria2c"的最短耗时地板就是 ~5.1s（启动 0.73s + 停止 4.2s）；UI 必须给"停止中…"的等待态，不能假设秒退。

**为什么不修**：这是上游 aria2 的行为，不在我们代码里。我们能做的是**别在等待期冻帧**（M2-3 已用 100ms 自驱重绘修掉"点停止后画面冻结 30s"）。

**该修的条件**：aria2 上游改动；或我们改走 `TerminateProcess`（**不采用**——会留下半写文件与控制文件，比多等 4 秒坏得多）。

## L6 「在线下载核心」在受限网络下不可用（线路1 长期 404、线路2 依赖 GitHub 可达）

**现象**：首次运行引导卡的在线下载，在本机实测**四条线路全失败**：

| 线路 | 结果 | 根因 |
|---|---|---|
| 线路1（`https://r.alusss.cn/` 前缀代理） | `AH-E3003` | 该域名对**所有路径**返回 CF 前置 nginx 的 404 HTML（1253 字节）——2026-11-22 侦察期即实测，从未可用 |
| 线路2（直连 GitHub release） | `AH-E6001 timeout` | 本机到 `github.com` 超时（`api.github.com` 可通，`github.com` / `release-assets.githubusercontent.com` 不通，2026-11-25 多次复现） |

聚合后为 `AH-E6007 全部下载线路失败`。**诚实失败，无假装成功**（失败路径行为是正确的）。

**影响**：在目标网络里「装完 → 面板自己下核心」这条路走不通，等于开箱不可用。

**处置**：首版改为**安装包自带 aria2c**（`task-54`），在线下载降级为「升级 / 换版本 / 补充」通道。自带后首次运行不再需要网络。

**已知的可读性欠账**（非缺陷，下一批改）：失败时用户看到的是三条线路的**原始错误串**，应合成一句人话（「在线下载不可用：镜像不可达、GitHub 不可达」）+ 可展开详情。

**该修的条件**：有可用镜像（含正确校验与 Content-Type 预检）；或换掉线路1 的域名。

## L7 「取消」撞上真实失败时，报失败而不是「已取消」（**设计语义，勿当 bug**）

**现象**：点取消后，若当前步骤在收尾前就**真的失败**了（例如取消恰好落在一次网络请求超时上），本次引导的结论是 `Failed(<原始错误>)`，而不是 `Cancelled`。

**为什么这样定**：`Cancelled` 的意思是「用户主动放弃，结果未知也不需要知道」。而这里我们**确知失败了**——把已知的失败抹成「你取消了」会丢掉信息，用户下次重试时也无从判断是网络问题还是自己点错了。

**判据**：取消是**请求**，不是**结论**。措辞上「已请求取消，当前步骤完成后停止」是准确描述（`task-52` 实测文案即如此）。

**该修的条件**：不修。若将来用户反馈困惑，改文案（「已取消（期间发生过一次网络失败）」），不改语义。

## L8 无交互桌面下「取消授权」与「弹不出授权框」不可区分（`ShellExecuteExW(runas)` 阻塞 122s 后返回 1223）

**实测（2026-11-25，锁屏/无交互桌面，v0.1.1 产物）**：面板点「安装为服务」→ `ShellExecuteExW(…, "runas", …)` **阻塞 122.29 秒**，随后返回 `LastError = 1223`（`ERROR_CANCELLED`，即「操作已被用户取消」）。

**同一条件下另一次实测（同日、另一会话、同一产物族）**：**300 秒内不返回**，既没有 `1223`、也没有任何结论 —— 说明「不返回」也是可能结局，而且时长不可预测（122s / ≥300s / 正常桌面上的秒级返回）。因此**不能**把某个固定秒数当成「用户拒绝」的判据。

**还有第三次观测**：`0.8s` 立即返回 `1223`。但那一轮的启动对象在被测工作区路径下，与「沙箱拦截从受管工作区发起的 ShellExecute」（见 `test.md` 6.7，同样返回 1223）混淆，**不能单独作为 UAC 行为的证据**。三次观测合起来只支持一个结论：**返回码与耗时都不可作为「用户是否拒绝」的判据**。

**含义一（架构约束）**：提权**必须**在后台线程执行。UI 线程同步调用 = 点一下假死两分钟；等待期间必须持续出帧并显示「已等 X.X 秒」。

**含义二（文案约束，重要）**：`1223` **同时**覆盖「用户点了取消」和「当前会话根本显示不出授权框（锁屏、无交互桌面、服务会话）」两种情况。因此：

- 文案**不许**断言「你拒绝了授权」；
- 正确写法：「已取消提权授权」+ 等待 ≥60s 时补一句「也可能是当前会话无法显示授权框（锁屏/远程/服务会话）」；
- 只出**信息条（灰）**，不出错误条（红）——它不是一个错误。

**影响范围**：面板「安装/卸载服务」、安装器的「同时注册为服务」勾选项。后者在无人值守安装（`/S`）里应当**默认不勾选**，否则会静默等两分钟。

**为什么不修**：这是 Windows 的返回值语义，不是我们的选择。我们能做的只有「不阻塞 UI」+「文案不冤枉用户」。

**该修的条件**：Windows 提供区分两者的 API；或我们改走服务助手（安装器 `runas` + 显式状态机，届时「取消」由我们自己的退出码表达）。

## L9 `--backend dx12` 私用工作集 116.4 MB，破 100 MB 闸门（EG-4）

**现象**：同一产物、K32 句柄口径、30 采样 / 60 s、单实例——显式 `--backend dx12` 的 PWS **随显示拓扑/会话状态漂移**：
**锁屏条件 116.4 MB**（116.3–116.6），**未锁屏且主屏是虚拟 IDD 时 88.8 MB**。同期 `vulkan` 在两种条件下都是
**51.6 MB**（不动），`auto` 收窄前 72.0 MB、收窄后 **51.4 MB**。即 **`dx12` = 88.8–116.4 MB**，
100 MB 闸门正好落在区间里——**同一台机器上加一条条件就能绿/红互换**。这不是「整组平移」：
`auto`/`vulkan` 稳定不变，只有 `dx12` 单点漂 27.6 MB，指向 DX12 路径对呈现面/DWM 分配敏感。

**已做的**：`auto` 收窄为串行探测、只开一个后端，且顺序是 **Vulkan → DX12 → GL**（内存优先），所以
**产品主路径不再走这条路**——本机 `auto` 落在 Vulkan，72.0 MB，余量 28 MB。DX12 只在 Vulkan 不可用时兜底。

> **写结论必须带条件**：`dx12` 的余量在锁屏条件是 **−16 MB**、在「未锁屏 + 虚拟 IDD 主屏」条件是 **+11 MB**。
> 只写「89 MB，没问题」会让下一个人拿错结论。测量脚本与文档里的每行判定都必须带
> `锁屏=… / 主屏=… / DPI=… / 采样=N / backend 实际=…` 元数据；缺元数据的读数按 INCONCLUSIVE 处理。

> **别把闸门看成绿的**：没有 Vulkan ICD 的机器（精简 VM、部分远程/虚拟显示适配器、Server Core 无 GPU）
> 会**回退到 DX12 = 116.4 MB，仍然超 100 MB 闸门**。本批只保证「有 Vulkan 的机器过闸门」，
> 「只有 D3D12 的机器过闸门」**没做到**。

**没做的**：没把 DX12 从枚举里删掉，也没能把 DX12 的内存压下来。差距（相对 Vulkan +65 MB）未逐项归因，
嫌疑是驱动侧工作集与交换链，需要 ETW / 供应商工具才能拆，不在本批预算内。

**该修的条件**：出现「只有 D3D12 可用」的真实机型（例如某些远程桌面 / 老 Intel 驱动），或产品决定
放弃 DX12 兜底。届时的选项：①继续查 DX12 内存；②接受该机型超闸门并在设置页如实标注；③把 D3D11/GL 做成兜底。

**复现**：`.scratch/m3/acceptance/` 下的三后端测量脚本，判 INCONCLUSIVE 的条件是采样<20 / 句柄取数失败>0 / 采样期实例数≠1 / 进程提前退出。

## L10 `--quit` 在极端情形下会让 CLI 回 `exit=2`（面板最终仍会退出）

**现象**：`--quit` 常规 ≈1 s；含停止链（保存会话 → `aria2.shutdown` → 三段式）实测 ≈6.3 s。
若 aria2 的优雅停止吃满 15 s 上限，总耗时会超过 CLI 的 10 s 等待预算，CLI 如实回
`quit: timeout` + `exit=2`——但面板**不会永久挂住**：ctl 线程的兜底网会把它退掉。

**为什么不现在修**：这 10 s 不是「面板慢」，是两个预算的职责错位——面板最坏路径
≈ `CONSUME_WAIT(2s)` + 停止链上限（15 s 优雅 + 10 s 强制）+ 宽限 ≈ 19 s，
而等待 `--quit` 的是**安装器的卸载/覆盖升级流程**（15 s）。该调的是安装器预算（提到的 20 s），
不是把 CLI 的 10 s 往上加 2 s——加 2 s 治不了 9 s 的差。CLI 的职责是「尽快如实回报」。

**什么条件下该修**：安装器等待预算调完（task-61）后本条删除；判据是极端情形下
安装器能等到面板退出，不再把「仍在收尾」误判成失败。

**证据**：task-59 真机矩阵（28 例，产物 sha256=`dfee696b…`，run 45587965652）。

**三条退出路（排障用：只看到一条日志时要能反推走的是哪条网）**

| # | 触发条件 | 日志特征（`ariahost.log`） | 典型耗时 |
|---|---|---|---|
| A 帧路径 | 正常：UI 在出帧 | `控制管道：收到 quit，走退出档` + `ctl.fallback: 未启用（帧路径已在 2s 内接手）` + `ctl.fallback: 帧路径已发出关窗…` | **≈1.0 s**（空载）/ **≈6.06–6.10 s**（含 aria2 停止链：2 s 停核 + 2 s 宽限 + 握手） |
| B 兜底（第一张网） | quit 后 2 s 内**没有帧**（窗口被遮挡 / 空闲定时器没排上） | `ctl.fallback: 2s 内没有出帧回执，改由 ctl 线程收尾` → `ctl.fallback: 开始收尾` → `ctl.fallback: 停止完成` | **≈3.04 s**（空载）/ 若 aria2 在跑则 +停止链 |
| C 第二张网 | 帧接住了、停止也做完，但 `ViewportCommand::Close` 被系统吞掉，此后不再出帧 | `ctl.fallback: 帧路径已发出关窗…` 之后紧跟 `ctl.fallback: 关窗后 2s 进程仍未退出 → 直接 exit 0`；或 app 侧 `退出：关窗 2 秒未生效（系统吞掉了 Close）→ 直接 exit 0` | 帧路径耗时 + **2 s** |

注：C 的两种文案分别来自 ctl 线程（WARN，`ctl.fallback` target）与面板自身（`panel` target）——两者都在，说明两张网同时到期，属正常（退出幂等）。

**实测分布（4a「下载中不信令」，含停止链，产物 `dfee696b…`，两轮各 10 次）**：20/20 `exit=0` 且面板必消失；耗时 最小 **5052 ms** / 中位 **≈6070 ms** / 最大 **6100 ms**，全部 < 10 s，无一例 `exit=2`。路径计数：A 帧路径 19 次、B 兜底 1 次（该次 aria2 未起，属空载）；C 第二张网**在本轮未被自然触发**（上一版产物曾 1/2 命中，故留网保留）。

### 取证开关：让 C 路径可以被强制复现（task-62）

C 依赖「系统吞掉 `ViewportCommand::Close`」，概率低且不可控，靠碰运气无法完成验收。因此提供一个**只用于取证**的开关：

| 取值 | 作用 | 走哪条路 |
|---|---|---|
| 未设置 / 空 / 拼错 | 完全不改变任何行为（拼错不猜，宁可不走取证分支） | 正常 A/B |
| `ARIAHOST_QUIT_SIMULATE=fallback` | 跳过「等 2 s 出帧回执」，直接由 ctl 线程收尾 | B |
| `ARIAHOST_QUIT_SIMULATE=close-swallowed` | 帧路径照常走完停止链、照常标记「已发出关窗」，但**截断**真正的 `Close`，且不让面板自己的看门狗兜底 —— C 成为唯一出口 | C |
| 旧变量 `ARIAHOST_QUIT_FALLBACK_SIMULATE`（非空即可） | 仍被识别，一律折算成 `fallback` —— 老取证脚本不会静默失效 | B |

生效时 `ariahost.log` 必有 WARN 一行：`退出：取证开关 ARIAHOST_QUIT_SIMULATE=<值>…`（target=`panel`）。
**纪律**：该变量只允许在取证脚本里设置，产品默认路径、安装器、服务都不能设它；设了就等于在测一条「现实中偶尔才发生」的路，读数不能当常规耗时。

**待回填**：C 行「典型耗时」目前是**推算值**（帧路径 + 2 s 关窗看门狗），尚未用 `close-swallowed` 在制品上实测。等带 task-62 的产物出来后按同一判据（`exit=0` + 面板消失 + 日志三段齐全）实测并把区间写回上表。

## L11 卸载器的注册表清除在真实用户机上**仍未取证**（已排除「是我们的缺陷」）

**曾经的现象**：`task-66` 的安装包端到端核验里，卸载后 `HKCU\Software\AriaHost` **仍然存在**。

**已查清：那对残留键不是卸载器留下的，是取证脚本自己写的** ——
1. 卸载段 [`installer/ariahost.nsi:939-940`](../../installer/ariahost.nsi) **无条件**删两个键（`${REG_APP_KEY}` 与 `REG_UNINST_KEY`），代码层面与「有没有探测到在跑的实例」无关；
2. `task-66` 的 harness（`t66-e2e.ps1`）在**安装前**就写了 `HKCU\Software\AriaHost\InstallDir`（为了让 `.onInit` 认沙箱目录），step 8 只还原了值、**没删键**；
3. 独立最小探针（只 `WriteRegStr HKCU` 一次）在本环境**返回 ERR** —— 说明 NSIS 子进程写 HKCU 在本会话被拦，卸载器既没写进去过，也就无法证明「删掉了」。

**所以现在的准确表述是**：`HKCU\Software\AriaHost` 残留 = 取证环境产物，**不是产品缺陷**；「真实用户机上卸载后键是否消失」**仍未验证**（本会话 NSIS 写 HKCU 被拦，无法构造）。

**什么条件下补验**：在**非沙箱**机器上装一次 per-user 包 → 卸载 → `reg query HKCU\Software\AriaHost` 与 `HKCU\...\Uninstall\AriaHost` 都查不到；同时确认 `%LOCALAPPDATA%\Programs\AriaHost` 已删、`<dl.dir>` 里的用户数据**未被触碰**。补验通过后删本条并记入修订记录。

**教训（值得单独记住）**：验收脚本自己的写入会伪装成「产品残留」。造 harness 时**凡写进被测系统的状态，必须在收尾时能证明已撤销**，否则结论只能写「未取证」，不能写「缺陷」——方法论见 [test.md](test.md) §6.13。

## L13 「核心运行中」最多晚 ~5.6 s 才显示（**设计如此**，不改固定 100 ms 轮询）

**现象**：`ariahost-core` 的启动就绪循环是**有界退避**——`Timeouts.poll=200 ms` 起步、每次 ×1.5、上限 `poll_max=1 s`，总预算 `ready=15 s`。所以 `getVersion` 探测发生在累计 **0 / 0.2 / 0.5 / 0.95 / 1.63 / 2.63 / 3.63 / 4.63 / 5.63 s …**。若 aria2 自己要到第 ~5 s 才应答 RPC，界面就会在第 ~5.6 s 才转「运行中」，用户看到「启动中」多停几秒。

**为什么不改**：这是**长时间驻留**的冷启动循环。改成固定 100 ms 会让 aria2 启动期间每秒 10 次 TCP+RPC 尝试，在服务形态/低配机上白烧 CPU；而 200→1000 ms 的退避在 15 s 预算内已覆盖 9 次探测。

**判据只认外部三段计时**（缺一段就不能下结论）：

| 段 | 定义 | 归属 |
|---|---|---|
| S0 | `T_spawn − T_click` | 我们的点击处理 + `CreateProcess`；> 300 ms 才是缺陷 |
| S1 | `T_RPC_ready − T_spawn` | **aria2 自身**的启动时长，不受我们控制 |
| S2 | `T_探测到 − T_RPC_ready` | 我们的探测间隔，**≤ 1 s 即合规** |

**什么条件下重开**：某真机三段计时里 **S2 > 1.5 s**（说明还有别的东西在压制探测），或「启动中」稳定超过 8 s 变成可复现现象。

## L14 服务形态的控制面**设计未决**（实施服务模式 RPC 之前必须先裁）

**现象**：控制管道名现在按**交互用户 SID** 隔离（`paths::control_pipe_name()`，与 L3 同一机制）。这套只对**面板形态**成立。**服务形态**跑在 Session 0 / LocalSystem：服务侧拿不到「当前交互用户」的 SID，要么用 SYSTEM 自己的 SID（那交互用户算出来的名字就不是它，`--quit` 永远打不开），要么枚举登录用户。

**今天为什么不会炸**：控制面目前只有**一个** verb `quit`，而服务形态不需要 `quit`（停服务走 SCM）。所以这是「实施服务 RPC 之前必须先裁」的前置项，已记入 `.scratch/m4/worklog-builder-svc-pipe-sid.md` §7；**现在不写代码、不预造管道**。

**两条候选**（实施时二选一）：
1. SYSTEM 侧用**另一个**管道名（如 `ariahost-ctl-service`），只对 `Interactive` 授 `OW`；交互侧先试本用户名、再试服务名。
2. 受 ACL 保护的**秘密文件**放限时令牌（写文件路径而不是管道名）。

**硬约束**：任何方案都不得让「普通用户能停别人的面板」，也不得为一次**零收益**的加固引入新机制。

**DACL 现状（2026-11-26 裁定保留 `BA`）**：交互管道 DACL 里保留 `Builtin\Administrators`。理由：摘掉它挡不住一个本来就能 `taskkill` 的管理员，安全收益为零；真正的缺陷实体是「交互用户越权停别人的面板」，而 `IU` 本来就未授权——那部分已成立。**不要为这条再开一次门禁 + CI。**
